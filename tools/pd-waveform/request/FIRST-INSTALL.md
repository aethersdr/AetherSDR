# Independent first installation (development)

The ARM64 development path passed clean installation, reboot persistence and
receive-only local DAX IQ qualification on a FLEX-8600 running 4.3.16.42034.
Installation used ordinary public waveform uploads, without an installed shim
credential or diagnostics bridge as its installation transport. This is a bench
qualification of the development candidate, not production or FLEX-6000 approval.

The latest [selected-IQ qualification](../FIRST-IQ-LIVE-QUALIFICATION.json)
covers runtime `88280414` through the desktop: an absent active predecessor,
new local identity, temporary-installer cleanup, one normal reboot with exact
commit readiness in 44.172 seconds, and complete 16,384-sample local DAX IQ
captures before and after reboot. FDX remained off and there was no RF.
The channel/pan identity matched each current GUI session. Final audits found
only three unprivileged control processes, no DSP/capture workers or local ARP
entry, and the same runtime hashes and identity after reboot.

That run used a fresh desktop profile. A reused profile correctly refused to
replace a completed first-install journal signed by an older development key.
Cross-publisher reinstall/recovery, interrupted updates, RF behavior and actual
FLEX-6000 hardware remain separate qualification gates.

The subsequent [channel and ownership qualification](../SELECTED-IQ-LIVE-QUALIFICATION.json)
captured channels 2–4 on that same installed runtime. Channel reassignment and
GUI disconnection terminated capture; an explicit new Start recovered with
the current binding. Host audits found no remaining IQ/DSP workers or temporary
ARP entry. Fault exits retained `cleanup_unconfirmed`; successful later normal
stops reported `stopped`. These receive-only observations do not qualify RF
unkey timing or simultaneous foreign-client conflicts.

## Authorization and identity

The operator approves a `PDFST001` plan bound to the radio serial, firmware,
signed release digest, new admin-token SHA256, hostname and random installation
ID. The publisher key is compiled into the native requester, delivery adapter and
worker. Artifact assembly does not grant consent. The qualification uploader
requires the exact plan digest through `--approve-plan`. The normal development
desktop instead previews and approves the exact plan through its installation
coordinator and stores the new credential in QtKeychain before uploading.
Neither path supplies the unfinished shipping package catalogue.

The first-install waveform contains public inputs only. Its shell entry uses
`exec` to start the fixed native requester and has an empty setup section. It
contains no bearer token, transport key, configurable commands or arbitrary
installer path. The CLI qualification client keeps the new bearer token in a
private client file. The desktop keeps it in QtKeychain and binds its reference to the durable
attempt journal before any upload; it is absent from public package bytes.

`pd-first-request` runs as UID 78666/GID 20 with no capabilities and NoNewPrivs.
It verifies the release, worker, plan and live radio identity, snapshots inputs
into unlinked RAM files, and generates a transport secret in RAM. A bounded
Unix broker grants that private descriptor once to each of two UID-0 roles:
accept and deliver. Incoming ancillary descriptors and repeated roles are
rejected. The carrier's public `PDFPUB01` record binds the worker and plan to
this attempt's nonce.

Unlike the installed-shim upgrade protocol, this path has no predecessor token
or published commitment to a secret generated by that predecessor. The initial
operator-approved public waveform upload is its authority boundary. A process
already running as the waveform UID can race or deny service, or invoke the
same exact approved job; it cannot replace the pinned plan or signed worker.
Do not represent this as stronger isolation between applications sharing that
UID. The normal waveform upload facility itself remains a privileged firmware
installation interface.

## Transaction and runtime

The explicit fresh plan is different from `PDMIG001`. A missing predecessor
never converts a migration into a fresh installation. First installation checks
that the legacy container is absent and refuses an unrelated installed store.
It stages and verifies the signed release, publishes its protected intent and
recovery capsule, then initializes a new private `provision.json` atomically.
Only the token hash is persisted. No prior identity files are copied.

The new identity starts in `local` state with an installation ID and authenticated
LAN control. It does not join a tailnet or create a Tailscale identity. Tailnet
sign-in is a separate operator action. The shim and AetherPD run as the ordinary
waveform user; fixed root boot/session adapters retain only their existing
bounded jobs. Removing the temporary carrier does not remove those fixed
adapters, because they are required at boot and for IQ session setup.

The worker verifies the running executable, selected payload and local identity
before committing. `first-selection` binds that selected payload record to the
plan. After commitment and cleanup, a root-owned RAM `PDVIEWF1` record allows
`GET /v1/aetherpd/installation` to report `first_install_plan_blake2b_256`, the
selected release and publisher key. The endpoint requires the new bearer token.
Delivery success and ordinary HTTP readiness are not commitment.

Interrupted installation uses the existing independent recovery service.
Recovery disables the new runtime and preserves the owned identity; it never
reconstructs an absent predecessor. Interrupted preparation may resume only
when its protected intent matches. A different attempt cannot adopt that store.
A terminal failed fresh installation can receive an explicit authenticated
same-plan retry grant through the bounded bootstrap delivery path. It preserves
the failed record and identity, and consumes the grant before forward work.
Boot recovery never grants or performs a retry; a different attempt cannot adopt
or erase the store. The failed-install retry qualification below covers this path.

## Qualification procedure

1. Obtain exclusive bench access. Confirm the
   current radio/firmware and receive state. Do not transmit.
2. Rebuild and verify the current candidate and record all artifact digests.
3. Preserve the old store, private identity and systemd units in a protected,
   recoverable backup. Remove them from the active paths and prove that the
   shim listener and old runtime are absent. Bench diagnostics may prepare this
   fixture, but may not deliver or authorize the new installer.
4. Use `run_first_install.py` with the exact reviewed plan digest. It uploads the
   public native waveform and per-attempt carrier through the normal radio API,
   then verifies authenticated commitment and the new identity. It uses no old
   shim credential, SSH or diagnostics bridge for installation.
5. Remove both temporary waveforms and independently audit capsule, installer
   process, broker, carrier/container and cached-artifact cleanup. Public
   uninstall acknowledgement alone does not prove cached files were deleted.
6. Reboot once. Verify a changed boot ID, the same new identity/token, an exact
   matching committed record, automatic startup and an unprivileged primary.
7. Start a bounded receive-only AetherPD session with FDX disabled. Prove local
   DAX IQ packet delivery and cleanup of the fixed ARP/capture resources. No RF
   correction claim follows from this receive-only test.
8. Save evidence and restore the protected old installation if qualification
   fails. Actual FLEX-6000 installation and Linux 2.6 behavior remain separate
   hardware gates; this initial requester supports ARM64 only.

## Firmware upload contract

Native packages use `file filename <name>.ssdr_waveform` followed by
`file upload <size> new_waveform`, and removal uses `waveform uninstall`.
Container archives use `file upload <size> waveform_docker_image <name>.tar.gz`
and `waveform remove_container`. They do not use the native upload route.
The native basename is alphanumeric: this firmware strips hyphenated prefixes
from legacy upload names, which prevents the matching archive directory from
starting. These commands agree with the existing WaveformInstaller and FlexLib
paths and were exercised on the bench.

The native requester does not register a DSP waveform, so public waveform
inventory is not its readiness signal. The authenticated handoff and exact
committed plan establish success. Optional `client program` labeling was refused
by this firmware in the receive proof; omitting that label allowed normal GUI
registration and IQ capture.

## Desktop commitment monitoring

`AetherPDInstallationMonitor::beginFirstInstallation` accepts the exact approved
`PDFST001` bytes, the new token and an independently trusted raw publisher key.
The token must hash to the approved identity. The plan has no predecessor or
publisher-key field; the key must come from authenticated package metadata,
never from the status response. Upgrade and first-install records remain
separate and cannot be converted implicitly.

The monitor accepts only a matching committed fresh record. Another attempt or
an upgrade record stays pending; changed target, selected release or publisher
fails the match. It performs bounded GET requests only. Both existing base64url
shim tokens and the fixed lowercase-hex first-install token format are accepted
by the common AetherPD transport policy. Malformed token syntax is rejected
before network access.

The `first-install-desktop-monitor` evidence directory records four registered
Qt test passes, scoped address/undefined/leak sanitizer checks, and a read-only
live match against the installed 8600. Package preparation, operator consent
and credential storage are connected and exercised in the desktop qualification below.

## Desktop package preparation

`AetherPDFirstPackage` authenticates a fixed eight-file snapshot: installation
worker envelope, candidate release, standalone requester, four carrier programs
and licenses. It uses independent size/SHA256 pins and a publisher key from the
application catalogue. The signed worker must have the installation role and
match the candidate release/source; it cannot be an upgrade worker. No
predecessor release or predecessor key is accepted. This path currently accepts
ARM64/profile 1 only.

Preparation takes the connected serial, new token hash, hostname and fresh
installation ID. It returns a public plan, the fixed native ZIP and the bounded
carrier image for review before operator approval. It receives no bearer token,
creates no transport secret, performs no network access and grants no consent.
The native archive has eight fixed files, an empty setup section, and an entry
script that only execs the authenticated requester. File modes and dates are
reproducible; no caller-controlled executable path or command is accepted.

`first-install-desktop-package/actual-validation.json` records local preparation
from the signed artifacts previously installed on the 8600. The native ZIP is
byte-identical to that installed artifact (9,085,612 bytes). Independent tar/OCI
inspection confirms identical carrier payload, modes, execution configuration
and rootfs digest. C++ builder provenance changes its config/image digest.
Three component test executables and scoped sanitizer checks pass; the ZIP and
carrier tests also pass in the full project's registered graph. These prepared
C++ archives were subsequently uploaded through the desktop workflow below.
The coordinator and credential model consume this preparation component.

## Desktop upload coordinator

`AetherPDInstallationCoordinator::prepareFirst` freezes a verified first package
with a fresh installation nonce. The caller must store the new credential and
obtain approval of these exact bytes before `begin`. Admission checks the new
token hash, current radio serial/firmware, original control session, receive
state and one-use preparation. It never obtains authorization from the old shim.

The coordinator reserves the radio's upload service for the exact native and
container filenames/sizes. The native transfer must receive its upload-port
acceptance and finish before a three-second startup wait and the one allowed
transition to the container transfer. The original reservation, session and
deadline remain unchanged. Other filenames, sizes, purposes, duplicates and
replacement sessions are refused. Temporary local files retain the approved
basenames under a private directory.

After carrier publication the coordinator uses only the authenticated read-only
first-install monitor. Upload completion is not commitment. Deadline expiry
enters cleanup before another stage can start. Cleanup requests removal of the
exact carrier and native helper, holding the reservation until container absence
and native uninstall acknowledgement are observed, or the cleanup deadline ends.
Cancellation does not assert that an independent on-radio worker cannot finish;
no automatic rollback or installation retry is issued. Destruction abandons
observation and retains the bounded upload settling window.

`first-install-upload-lifecycle` contains registered project tests for admission,
ordering, cancellation, destruction, deadline and session loss. These are
injected-transport component proofs. Public cleanup confirmation means the
removal observations above; it does not prove cached firmware files or private
host processes were removed. The live desktop qualification below includes a
separate host audit of those artifacts.

## Desktop credential model

`AetherPDInstallationModel::prepareFirstPackage` accepts only an independently
verified first package. It generates a fresh 256-bit token in memory and prepares
the immutable plan off the UI thread using only its hash. Preview and approval
remain bound to the original radio session. No credential read, write, upload or
RF command occurs during preparation.

Exact-plan approval first writes the token to QtKeychain service `AetherSDR`, key
`aetherpd/first/<SHA256(serial + '/' + planDigest)>/admin_token`. This separate,
per-attempt slot preserves existing active credentials. A positive persistent
write completion is required before the coordinator starts; session-only fallback,
write failure, timeout, cancellation and replacement sessions cannot start it.
Late callbacks are generation-fenced. The key is also reserved by the settings
credential policy, so it cannot become an ordinary settings/export value.

After the coordinator observes the exact committed plan, the model writes that
token to the existing per-radio TailnetShim slot. Failure or timeout here leaves
the confirmed installation outcome intact and reports a separate credential
failure. The attempt slot is retained; cancellation and uncertain installation
outcomes do not delete the only recovery credential. No failed or canceled
installation promotes a token. The model and dialog expose the saving and
promotion states and describe first-install authority separately from upgrades.

`first-install-credential-model` records three registered suites, two scoped
ASan/UBSan/LSan suites, and a mutation that removes the durable-write gate and is
detected. The tests inject keychain callbacks; they do not establish a working OS
keychain on every supported desktop. The Linux QtKeychain backend was checked with an isolated credential written,
read and deleted by separate processes. The Linux live desktop workflow below
uses its actual durable credential. Other desktop platforms remain unqualified.

## Public attempt journal and restart observation

After durable token storage, first-install approval records the exact public plan
and independently trusted publisher key in the radio-scoped `AetherPDInstallation`
settings document (schema 1). Failure stops before upload. The document contains
no bearer credential. Unknown schemas, malformed records and different pending
attempts are refused. Compare-and-set runs the expected-record check and write
inside one SQLite `BEGIN IMMEDIATE` transaction, preventing stale writers from
overwriting another desktop process's record.

`recoverFirstInstallation` requires a fresh current radio session and a publisher
key supplied by the application's trusted catalogue. It never adopts the stored
key as its trust source. The exact serial and firmware must match, and the token
loaded from the attempt's keychain slot must hash to the approved plan. Recovery
then starts only the existing authenticated GET monitor. There is no installer
retry, upload, radio cleanup, rollback or RF command. Cancellation or session loss
abandons observation without altering the pending journal.

Exact committed observation permits active-credential promotion. Only a durable
promotion updates the journal to `credentialSaved`; a failed journal update stays
unresolved. Recovery cannot attest temporary-component cleanup and reports that
separately. The development UI uses the pinned selection below. This is not a complete
shipping recovery qualification.

## Development desktop controls

`AETHERPD_FIRST_DEVELOPMENT_SELECTION` accepts a reviewed build-time JSON file
with `version`, `firmware`, `profile: 1`, `publisher_key`, and exactly eight `files`
size/SHA-256 pins. Files reside in its sibling `package` directory. The generator
compiles those pins and the publisher key into `AetherPDFirstDevelopmentSelection.h`;
runtime manifests/environment never establish trust. The first-install schema
rejects predecessor fields and upgrade packages. CMake marks these builds as
non-shipping. Ordinary builds expose dimmed controls with a stated reason.

**Prepare first installation** verifies and freezes the package off the UI
thread, generating a token only in RAM. **Approve first installation** approves
exact displayed bytes, then durably saves the token and journal before upload.
The preview names the temporary host-root actions, retained fixed helpers, new
local hostname and authenticated package identifiers. It does not use an old
shim credential. **Check saved installation** uses the compiled publisher key and
only the read-only recovery path. A saved attempt disables first-install
preparation; recovery never becomes an implicit reinstallation.

`first-install-desktop-controls` records default-build disabled-control checks,
configured-fixture preparation/recovery checks, a rendered panel and an isolated
real OS-keychain write/read/delete across separate processes. The normal UI and

## Resuming a pending desktop attempt

**Prepare saved attempt** requires a pending journal for the current radio and
firmware plus independently trusted package pins. It loads the per-attempt
credential and verifies its hash against the saved plan. The existing hostname,
installation nonce, release and package names are reconstructed exactly; changed
release bytes or publisher keys are refused. There is no new random identity.
Preparation is local and does not upload or rewrite the credential.

**Approve saved attempt** atomically compares the current pending journal before
starting delivery. A completed or replaced record is rejected. The loaded
credential was already durably stored, so this path does not rewrite the attempt
keychain slot. Normal exact-plan commitment, active-credential promotion and
public cleanup still apply. The shared upload reservation excludes overlapping
installs, and a present carrier is not removed to force a retry.

An unreachable status endpoint is not evidence of an absent installation. The
native worker binds re-entry to the existing protected plan, reconciles an
interrupted transaction and refuses unrelated stores. A terminal committed
transaction only completes cleanup; it is not reinitialized. A terminal failed
fresh transaction remains failed unless the explicit same-plan delivery obtains
the protected one-use retry grant described below. Status polling and boot
recovery cannot grant it. This action does not erase identity or adopt another plan.

## Failed fresh-install retry component

The current native source supports an explicit redelivery retry of a terminal
failed `PDFST001` transaction. The separately signed
`0.0.0-retry.d60df159f` candidate is built and independently pinned in the
qualification desktop; its native signatures and three desktop test suites pass.
Its release is 9,005,703 bytes. Assembly with identical inputs was reproducible;
complete binary rebuild reproducibility has not been tested. The candidate is now
installed on the 8600; its separate failed-transaction retry qualification is below.
The ordinary pending-upload resume proof above exercises a different interruption.

Only the authenticated bootstrap delivery path can publish `transaction-retry`.
It requires the exact terminal failed fresh plan, republishes the bounded
recovery capsule, and holds the exclusive transaction lock while preserving the
old failed journal in `transaction-failed`. A migration or committed transaction
cannot receive this grant. The marker and its partial publication are fixed-size,
root-owned, mode 0600, single-link files; foreign bytes and unsafe metadata are
preserved and refused.

A normal worker consumes and directory-syncs the grant before taking any forward
step. A crash after consumption cannot reuse it. An interrupted marker publication
never authorizes a forward step. Boot recovery consumes/discards the grant and
cleans the already failed transaction; it does not retry installation. The new
forward transaction uses the original plan, token hash, hostname and installation
ID. Existing identity bytes must still match; the retry never erases or adopts
another identity. The old failure record remains after success. Repeated failures
reuse these bounded records rather than accumulating a history directory.

This keeps the existing public-upload authority boundary. It does not provide
cryptographic operator isolation from another process already sharing the waveform
UID and able to redeliver the same exact approved job. It grants no arbitrary
command, path, different payload or different identity.

`first-install-failed-retry-development` records 46 whole-worker namespace tests,
26 transaction tests, transaction ASan/UBSan/LSan passes, ARM64 worker and Cortex-A8
ARMv7 boot-helper builds. The tests cover boot refusal to advance, interrupted
publication/consumption, metadata and lock refusal, identity and selection
preservation, and committed redelivery without reactivation. A separate mutant
that accepted a partial retry marker as authorization was rejected by the regression.
The radio and service adapters in whole-worker tests are fixtures; this is not
physical power-loss or FLEX-6000 hardware qualification. Live retry evidence is
recorded separately below.

## Disappeared-carrier cleanup regression

The fixed desktop requests removal once for a carrier it previously observed,
even if firmware reports that carrier removed before cancellation. It requires
an accepted removal reply and current absence before confirming public cleanup.
A carrier that was never observed remains unconfirmed; cleanup does not recreate
or re-upload it. Rejected and missing replies cannot become success.

A separate inert fixture on FLEX-8600 4.3.16.42034 demonstrated why both steps are
needed: a stopped container produced a `removed` waveform status while its exited
container and image remained. The ordinary `waveform remove_container` request
then removed both. The installed shim retained its PID and identity throughout.
This does not change the earlier image-only negative result: a list omission
alone is still not an independent container/image audit.

`DISAPPEARED-CARRIER-CLEANUP-QUALIFICATION.json` records the desktop regression
and repeated live failed-install test. The new injected-transport regression fails
against the prior implementation because no removal request is sent. A separate
mutation that bypasses the acknowledgment gate also fails. The three installation
suites and full desktop build pass.
